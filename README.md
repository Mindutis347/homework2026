# Keyforge — a digital game key marketplace (Eneba internship assignment)

A production-shaped marketplace for digital game keys: browse the catalog, search with typos,
compare offers from several sellers, check out, and get an instant key — plus a merchant portal
for sellers and an admin back-office for the platform.

**Live:** [keyforge-blush.vercel.app](https://keyforge-blush.vercel.app) · API: [keyforge-api-fra.onrender.com](https://keyforge-api-fra.onrender.com/api/health)

Demo accounts (also listed on the sign-in page):

| Role | E-mail | Password |
|---|---|---|
| Buyer | `demo@keyforge.dev` | `Demo#2026` |
| Seller | `seller1@keyforge.dev` | `Seller#2026` |
| Admin | `admin@keyforge.dev` | `Admin#2026` |

Checkout is simulated: any card number works except one ending `0002`, which exercises the
decline path. Verification codes are shown in-app (simulated inbox) instead of being e-mailed.

- **Frontend:** React 19 + TypeScript + Vite + Tailwind CSS (Vercel)
- **Backend:** Go (stdlib `net/http`) + `pgx/v5`, hand-written SQL (Render)
- **Database:** PostgreSQL (Neon) with the `pg_trgm` extension

## Running locally

```bash
# backend
cd backend
cp .env.example .env      # then set JWT_SECRET (DATABASE_URL comes from .env.local)
go run ./cmd/api          # migrates + seeds on boot, serves :8080

# frontend
cd frontend
npm install
npm run dev               # http://localhost:5173
```

The Go config merges `.env.local` and `.env` (real environment variables always
win), so the Neon CLI can own the connection string while `.env` holds the rest.

## Deployment

**API — Render.** `render.yaml` defines the service (root `backend`, health check
`/api/health`). Set in the dashboard:

| Variable | Value |
|---|---|
| `DATABASE_URL` | Neon pooled connection string (`?sslmode=require`) |
| `JWT_SECRET` | generated by Render from the blueprint |
| `COOKIE_SECURE` | `true` (cross-site cookies need Secure + SameSite=None) |
| `CORS_ORIGINS` | the Vercel URL, e.g. `https://keyforge.vercel.app` |
| `SEED_ON_BOOT` | `true` (seeds once, then no-ops) |
| `SHOW_DEV_CODES` | `true` for the demo (verification codes visible) |

**Frontend — Vercel.** Import the repo, set root directory to `frontend`.
`vercel.json` handles the Vite build, the SPA rewrite, and — importantly — proxies
`/api/*` to the Render service so the browser only ever talks to one origin.

**Why the proxy:** the session cookie is `HttpOnly` and, across two different
sites (`*.vercel.app` → `*.onrender.com`), it would be a *third-party* cookie,
which browsers now block by default. Routing `/api` through Vercel makes the
cookie first-party, removes the CORS preflight, and keeps the token out of
JavaScript's reach. Because of this, **no `VITE_API_URL` is set in production** —
the client uses relative `/api` paths. Set `VITE_API_URL` only if you host the
API and frontend under the same site another way.

## API surface

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/health` | — | liveness + DB ping |
| GET | `/api/homepage` | — | all visible homepage blocks with resolved products |
| GET | `/api/products` | — | catalog: search, platform/region/genre/price filters, sort, pagination |
| GET | `/api/products/{slug}` | — | product detail + offers grouped by platform/region |
| GET | `/api/search` | — | fuzzy search (trigram) with suggestions |
| POST | `/api/auth/register` | — | create account, issues verification code |
| POST | `/api/auth/verify` | — | confirm 6-digit code |
| POST | `/api/auth/login` | — | sets httpOnly session cookie |
| POST | `/api/auth/logout` | user | clears cookie |
| GET | `/api/auth/me` | optional | current user |
| GET/POST/PATCH/DELETE | `/api/cart` | user | cart contents |
| POST | `/api/checkout` | verified user | simulated payment, atomic key delivery |
| GET | `/api/orders` | user | order history with keys |

Merchant and admin routes are documented in `docs/api.md`.
